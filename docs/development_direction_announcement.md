## 1. 現在の理解状況

本プロジェクト `japan-cvd-risk-simulator-meds` の計算ロジックについて、以下を理解しました。

### 1.1 アプリの目的

薬剤を追加した場合の心血管イベント（心筋梗塞・脳卒中・全死亡）リスクと費用をシミュレーションする、患者との共有意思決定支援ツール。

### 1.2 計算フロー

```
1. 患者プロフィール・リスク因子入力
   └─ 年齢、性別、SBP、LDL、HbA1c、喫煉、BMI、CKD 等
2. 薬剤選択
   └─ Excel から読み込んだ薬剤カタログから選択
3. 目標値自動生成（meds_catalog.py）
   └─ SBP: 効果量を足し算
   └─ LDL: 低下率を掛け算
   └─ HbA1c: 効果量を足し算
4. リスク計算（calc_engine_outcomes.py）
   └─ 基礎発生率 × 個人の相対リスク = 年間リスク
   └─ 年次リスクを積分して累積リスクを算出
5. 結果表示
   └─ リスク比較サマリー / 費用 / 副作用 / 累積リスク曲線
```

### 1.3 核心となる数式

- **基礎発生率**: 年齢・性別別の CSV データを線形補間（または指数近似）
- **統合相対リスク**: SBP・LDL・HbA1c・BMI・CKD・喫煉の RR/HR を掛け合わせる
- **年間発症リスク**: `q(t) = 1 - exp(-h₀ × RR)`（MI・脳卒中）、`q(t) = h₀ × RR`（死亡）
- **累積リスク**: `P(T) = 1 - Π(1 - q(t))`

### 1.4 注意点

- `config.yaml` の `age_effect` は未使用で、実際の年齢減衰は `_alpha_by_age()` でハードコードされている
- MI・脳卒中と死亡で基準発生率の解釈が異なる
- PC版のサマリーとグラフで計算関数が異なる（BMI/CKD 反映の有無）
- 薬剤効果は単純な足し算・掛け算で、相互作用は考慮していない

## 2. 今後の開発方向性

### 2.1 背景

現在のアプリは「薬を全く使っていない状態から薬を追加する」前提で設計されている。しかし、実臨床では以下のニーズが多い。

- 患者はすでに複数の薬を服用している
- 「もう1つ追加すべきか」を検討したい
- 「この薬を減らせないか」を検討したい
- 費用対効果を含めて患者と対話したい

### 2.2 目指す機能

**「患者の現在の服薬状態（＝現在の薬費）を基準にして、薬を追加・減少させた場合のリスク変化と費用変化を可視化する」**

具体的には以下の3パターンを1つのUIで扱えるようにする。

1. **追加シミュレーション**: 現在の服薬 ＋ 新薬1つ → リスク低下・費用増加
2. **減少シミュレーション**: 現在の服薬 － 1剤 → リスク上昇・費用削減
3. **入れ替えシミュレーション**: 現在の薬A → 新薬B → リスク変化・費用変化

### 2.3 基本概念の変更

| 概念 | 現状 | 拡張後 |
|---|---|---|
| **Baseline（現在）** | 薬なしまたは手動目標値 | 患者の**現在の実際服薬状態** |
| **Target（将来）** | 追加後の目標値 | 追加・減少後の服薬状態 |
| **費用の見え方** | 「追加すると〇〇円かかる」 | 「〇〇円 → △△円（±差分）」 |

### 2.4 採用予定の設計方針

**調整差分（Delta）モデル + ハイブリッド実装** を採用予定。

```
baseline = 現在の測定値（= 現在の服薬状態を反映済み）
target   = 現在の測定値 ＋ 薬剤変更差分
```

このモデルのメリット：

- 患者の実測値をそのまま baseline として使える（臨床的に自然）
- 既存の薬追加モードも自然に包含できる
- `calc_engine_outcomes.py` の既存計算式は変更せず、新しいメソッドを追加する形で対応

### 2.5 変更予定ファイル

| ファイル | 変更内容 |
|---|---|
| `calc_engine_outcomes.py` | 新メソッド `cumulative_incidence_with_adjustment()` を追加。既存メソッドの中身は変更しない |
| `meds_catalog.py` | 新しい `MedicationAdjustment` class を追加 |
| `app_streamlit_outcomes.py` | モード切り替え、二重薬剤選択、費用比較表示 |
| `app_streamlit_mobile.py` | 同上（モバイルレイアウト版） |

### 2.6 UI のイメージ

```
💊 薬剤シミュレーション
├── [ モード選択 ] 薬を追加する / 薬を増減させる
│
├── 【薬を追加するモード】
│   └── 追加する薬を選択
│
└── 【薬を増減させるモード】
    ├── 現在服用中の薬を選択
    └── 変更後に残す薬を選択
```

費用表示例：

```text
💴 費用比較
- 年間薬剤費（現在の服薬中）: 120,000 円/年
- 年間薬剤費（変更後）: 72,000 円/年
- 費用変化: -48,000 円/年
```

## 3. 期待される効果

1. **共有意思決定の支援**: 患者と「リスク vs 費用 vs 副作用」を可視化しながら対話できる
2. **過剰投薬の見直し**: 減薬のリスクを定量化し、無理のない減薬を支援
3. **費用対効果の可視化**: 1剤あたりのリスク変化と費用を明確にできる
4. **患者理解の向上**: 「なぜこの薬が必要か」を数値で説明できる

---

## 4. 注意点・制約

1. 薬剤効果は単純な足し算・掛け算で、相互作用や ceiling effect は考慮しない
2. 費用は薬価の合算であり、診療報酬・検査費用は含まない
3. 教育・対話支援目的であり、医療機器ではない
4. 既存の薬追加モードは維持し、後方互換性を保つ

### PDF記入機能の概要

実診療で使う帳票にシミュレーション結果を転記する手間をなくすことが目的。
ひな型2種を実測したところ、内部構造が異なり実装方式が2通りに分かれる。

- `2026療養計画書v1.2.pdf` … **AcroForm形式**（フィールド90個）。
  pypdfの `update_page_form_field_values()` でそのまま記入でき、**こちらを先に実装する**。
- `生活習慣病管理.pdf` … **フラットPDF**（フィールドなし）。
  reportlabで描画したレイヤーを重ねるoverlay方式が必要で、座標の目視特定に工数がかかる。

> **順位3との関係**: HbA1cパースバグが未修正のままPDF出力すると、誤ったHbA1c目標値が
> 帳票に印字される。PDF機能の公開前にバグ修正を済ませるか、HbA1c欄を記入対象から
> 外す判断が必要（`pdf_form_fill_plan.md` 6章）。

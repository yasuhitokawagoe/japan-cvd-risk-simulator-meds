## 0. 決定事項（2026-07-21 確定）

| # | 論点 | 決定 | 理由 |
|---|---|---|---|
| 1 | 患者識別情報（氏名・生年月日） | **PDFでは空欄。手書きで補う** | アプリはRailwayで公開中。患者情報をサーバーに一切載せない |
| 2 | 記入対象の範囲 | **アプリが既に持つ値のみ（約20〜30欄）** | まず動くものを完成させる。行動目標・食事・運動欄は対象外 |
| 3 | フィールド名→意味の対応づけ | **Claudeが実物PDFを読んで候補表を作り、ユーザーが確認・修正** | フィールド名が `チェックボックス11` 等で意味不明。ゼロから人手で埋めるより速い |
| 4 | 実装対象アプリ | **PC版（`app_streamlit_outcomes.py`）先行 → モバイル版へ横展開** | 記入ロジックは共通モジュール化するので二度手間にならない |
| 5 | 出力フロー | **確認画面で記入内容を表示 → ダウンロード** | 診療記録になる文書。誤記入に気づけるワンクッションを入れる |

決定1の帰結として、**この機能はRailway公開版にもそのまま載せられる**（患者情報を扱わないため）。

### Step 3 — `pdf_fill.py` の実装

| 項目 | 内容 |
|---|---|
| 成果物 | `pdf_fill.py`（新規・PC版とモバイル版で共有する単一モジュール） |
| 中身 | ① アプリの状態 → フィールド値への変換 ② pypdfでの記入処理 |
| 完了条件 | 単体で呼び出して、対応表どおりに記入されたPDFが出る |
| 判断 | 不要 |
| **コミット** | 中身の①②で2分割する。**C3a**: `feat(pdf): アプリ状態→フィールド値への変換ロジックを追加` — 純粋関数＋ `tests/test_pdf_fill.py`（PDF不要でテストできる部分）。**C3b**: `feat(pdf): pypdfによるAcroForm記入処理を追加` — CB ON値の動的読み出し・`NeedAppearances` 設定を含む |

分割の理由: ①は「どの値をどの欄に入れるか」（間違えると誤った診療文書が出る）、
②は「PDFに書けるか」（間違えると動かない）。**失敗の質が違うので、切り分けられる形で残す。**
①だけをテストで固められるのも利点。

実装上、`pdf_form_fill_plan.md` 2.2 の実測事項を必ず守る:

- **チェックボックスのON値をハードコードしない。** ON値は `/Yes` ではなく「はい」のUTF-16BE表現。
  ひな型から動的に読み出す
- **`NeedAppearances = true` を立てる**（フォント未埋め込みへの対策）
- ドロップダウンは編集可能コンボボックスなので、選択肢に無い数値も書き込める

## 3. コミット方針

### 粒度の原則

1. **1コミット＝1つの完了条件。** 「動く単位」で刻む。途中の状態はコミットしない
2. **失敗の質が違うものは混ぜない。** 「値の対応づけの誤り（診療文書に実害）」と
   「PDF出力の不具合（動かないだけ）」は別コミットにする
3. **人の判断が入った箇所は独立させる。** 誰がいつ何を確定したかを `git log` に残す
4. **生成物（記入済みPDF）はコミットしない。** 出力先を `.gitignore` に入れる。
   ひな型PDF（`docs/pdf_forms/*.pdf`）は入力なのでコミット済みでよい
